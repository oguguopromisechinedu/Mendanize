# Mendanize Engineering Specification (MES-033)
## Caching & Performance

**Version:** 1.0 — rightsized from the pasted "Enterprise Caching & Performance Architecture" (MES-036). Kept: content caching, AI response caching (the one genuinely valuable idea — avoiding repeat AI provider costs for the same question), cache invalidation on publish. Dropped: ten separate named cache services, edge/CDN/distributed cache prep, sub-100ms performance targets that don't match this stack.
**Dependencies:** MES-002 (Shared Services), MES-017 (Search), MES-031 (AI Knowledge Pipeline — this is where AI response caching actually earns its keep), MSEM Appendix A

Follows MSEM Appendix A — this spec's targets are additions to, not replacements for, the Appendix's Performance Standard.

---

## OBJECTIVE
Cache what's expensive to recompute — published content queries and AI responses — without over-building a caching layer this platform's traffic doesn't yet need.

---

## CONTENT CACHING
Cache reads for: Homepage configuration, Navigation structure, published Articles/Guides/AI Tools, Category/Topic listings — all via the Content/Homepage/Navigation Services (MES-002). Standard Next.js data caching is sufficient; no separate cache infrastructure needed yet.

## AI RESPONSE CACHING (the important part)
This is where caching actually saves money: per MES-031's pipeline, once a question is answered from existing knowledge (Step 3) or a new draft is generated and published (Step 9), the same or similar future question should hit the Content Service's search first and never re-trigger AI generation. This is really MES-031's knowledge-reuse logic — this spec just confirms the caching layer supporting it (search results, not raw AI text) is fast enough not to be the bottleneck.

## CACHE INVALIDATION
On publish/update (Article, Guide, AI Tool, Homepage section, Navigation change), the relevant cached read is invalidated immediately — no stale content visible after a successful publish. This is the one hard requirement; get this wrong and admins won't trust the CMS.

## PERFORMANCE TARGETS (realistic, not enterprise)
Homepage < 1.5s, Article pages < 2s (matches Appendix A's general standard — no stricter target manufactured here), Search < 500ms (matches MES-017's existing target).

---

## WHAT NOT TO BUILD
Distributed/edge cache infrastructure, ten named per-domain cache services, sub-100ms targets, CDN integration (real infra work, not a spec-level concern yet).

---

## ACCEPTANCE CRITERIA
✓ Content reads cached with correct invalidation on publish. ✓ AI knowledge reuse (MES-031) confirmed fast enough not to block. ✓ No stale content after publish. Zero build/TS/lint errors.
