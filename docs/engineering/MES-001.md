## PURPOSE

This specification establishes the foundation, vision, architecture, engineering principles, and long-term direction of Mendanize.

Every future engineering specification (MES-002 and above) must follow this document. If any future specification conflicts with MES-001, this document takes precedence unless explicitly superseded by a newer engineering specification.

## PRODUCT VISION

Mendanize is not a traditional blog.
Mendanize is not a CMS.
Mendanize is not a public publishing platform.

Mendanize is an AI-powered technology learning platform that helps people understand modern technology through educational content, curated resources, AI assistance, structured learning, and intelligent discovery.

The platform should make complex technology easy to learn while maintaining professional quality suitable for beginners, professionals, creators, entrepreneurs, students, and developers.

Every engineering decision must reinforce this mission.

## PLATFORM ARCHITECTURE — TWO SURFACES, ONE PRODUCT

Mendanize is built as two distinct but connected surfaces. This split is foundational and governs all future specs (MES-002 and above).

### Surface 1: Teaching Frontend (mendanize.com)

- **Purpose:** where users *learn* — discover, read, get oriented.
- **Access:** public, no login required.
- **Pillars served:** Learn, Discover, Explore.
- **Content:** articles, learning guides, AI tool directory, topic and category pages, search.
- **Layout model:** Public Layout — Header, Main Content, Footer.

### Surface 2: Dashboard (App)

- **Purpose:** where users *do* things — use AI tools, manage content, track progress.
- **Access:** auth-gated. Session ownership is defined in **MES-006** (`features/authentication`) — do not invent a parallel auth stack in later specs.
- **Pillars served:** Practice, Ask.
- **Content:** user's own data, tool outputs, saved work, learning progress.
- **Layout model:** Dashboard Layout — Sidebar, Top Navigation, Main Content.

### How the surfaces connect

- Every teaching-frontend page (an article, an AI tool profile) should provide a clear path into the dashboard — e.g. "Try this in your workspace" — so learning converts into product usage.
- The dashboard's "Ask Mendanize AI" feature should pull context from teaching content where relevant, rather than duplicating explanations that already exist on the public side.
- Both surfaces share one design system (tokens, typography, color) but maintain distinct layout shells suited to their purpose (editorial vs. application). Per the Design Customization Principle, this shared design system is data-driven — both surfaces read the same live settings store rather than each holding its own fixed values.
- Content types (Articles, Learning Guides, AI Tools, Categories, Topics, Authors) are modules that must be addressable from both surfaces without duplicating data models — the teaching frontend reads them publicly; the dashboard reads them in authenticated context.

This two-surface model does not replace the module list below — it defines *where* each module is surfaced.

## DESIGN CUSTOMIZATION PRINCIPLE

Mendanize is a fully custom-built platform, not a template or theme. Because of this, nearly every visual aspect of the site can be exposed as an admin-configurable setting rather than a hardcoded value.

This applies across both surfaces (Teaching Frontend and Dashboard, per Platform Architecture below):

- Brand assets (logo, favicon, colors, fonts)
- Theme presets (light/dark, palettes)
- Backgrounds (solid, gradient, pattern, image, video, animated)
- Typography (font selection, heading/body styles, sizes, spacing)
- Components (buttons, cards, forms, badges, modals — style, not behavior)
- Animation (hover effects, transitions, loading states)
- Navigation (header, footer, navbar, sidebar, menus)
- Homepage layout (section order, visibility)
- Blog/article appearance (layout, code block style, author cards, related content)
- Dashboard appearance (colors, widgets, analytics layout)
- SEO & social defaults (OG images, favicons, metadata)
- Media library (images, icons, video, illustrations)
- Design tokens (spacing, radius, shadows, breakpoints)

**What stays fixed, owned by developers, never exposed as a setting:**
- Underlying UI architecture and component logic
- Responsive behavior
- Accessibility behavior (semantic structure, keyboard nav, focus handling)
- Data models and business logic

The boundary is: *how something looks and whether it's visible* is configurable; *how something behaves and is built* is not. This mirrors how Notion, Shopify, and similar platforms balance flexibility with a consistent, polished product.

The full technical design for this system (storage, application mechanism, admin UI) is defined in **MES-004**. Every subsequent spec that touches visual design must state which of its decisions are fixed defaults vs. admin-configurable settings governed by MES-004.

## ENGINEERING PRINCIPLES

Every engineering decision should follow these principles:

- Build for long-term maintainability.
- Prefer reusable components.
- Avoid duplicated logic.
- Write readable code.
- Keep modules independent where possible.
- Favor composition over unnecessary complexity.
- Optimize performance by default.
- Follow consistent naming conventions.
- Design for future scalability.
- Prioritize developer experience.
