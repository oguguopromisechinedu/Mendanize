## PURPOSE

This specification establishes the foundation, vision, architecture, engineering principles, and long-term direction of Mendanize.

Every future engineering specification (MES-002 and above) must follow this document. If any future specification conflicts with MES-001, this document takes precedence unless explicitly superseded by a newer engineering specification.

## PRODUCT VISION

Mendanize is not a traditional blog. Mendanize is not a CMS. Mendanize is not a public publishing platform.

Mendanize is an AI-powered technology learning platform that helps people understand modern technology through educational content, curated resources, AI assistance, structured learning, and intelligent discovery.

The platform should make complex technology easy to learn while maintaining professional quality suitable for beginners, professionals, creators, entrepreneurs, students, and developers.

Every engineering decision must reinforce this mission.

## PLATFORM ARCHITECTURE — THREE SURFACES, ONE PRODUCT

Mendanize is built as three distinct but connected surfaces. This split is foundational and governs all future specs (MES-002 and above). **This corrects the original two-surface model** — as written through v2.1, "Dashboard" ambiguously meant both "where learners practice and ask" and "where admins manage the platform." Once MES-030 (Dual Authentication) established that `/dashboard/`\* is `Admin`-only, the learner-facing half needed its own name and route — that's the Learner Account Area below, matching what MES-021 (Billing) and MES-022 (Personalization) already correctly build against.

### Surface 1: Teaching Frontend (mendanize.com)

- **Purpose:** where users _learn_ — discover, read, get oriented.
- **Access:** public, no login required.
- **Pillars served:** Learn, Discover, Explore.
- **Content:** articles, learning guides, AI tool directory, topic and category pages, search.
- **Layout model:** Public Layout — Header, Main Content, Footer.

### Surface 2: Learner Account Area (`/account/*`)

- **Purpose:** where an authenticated learner _does_ things — asks questions, saves content, tracks progress, manages billing.
- **Access:** auth-gated as a `PublicUser` (MES-006/MES-030) — never an `Admin` session.
- **Pillars served:** Practice, Ask.
- **Content:** the learner's own saved articles/guides/tools, Ask Mendanize AI (Tier 2, MES-019), learning history and interests (MES-022), subscription/billing (MES-021).
- **Layout model:** Account Layout — distinct from both the Public Layout and the Admin Dashboard Layout.

### Surface 3: Admin Dashboard (`/dashboard/*`)

- **Purpose:** where staff _manage_ the platform — content, users, settings, AI configuration, analytics.
- **Access:** auth-gated as an `Admin` (MES-006/MES-030) — never a `PublicUser` session. No self-registration; accounts are created only by a Super Administrator.
- **Pillars served:** none directly — this surface exists to operate the platform that serves the five pillars, not to serve them itself.
- **Content:** Article/Guide/Tool management, Categories/Topics, Media Library, SEO, Homepage/Navigation configuration, AI Studio, AI Knowledge Center, Platform Settings, Analytics, Billing reporting (read-only).
- **Layout model:** Admin Dashboard Layout — Sidebar, Top Navigation, Main Workspace, Right Context Panel, Status Bar (per MES-007).

### How the surfaces connect

- Every teaching-frontend page (an article, an AI tool profile) should provide a clear path into the Learner Account Area — e.g. "Save this" or "Ask about this" — so learning converts into product usage.
- Ask Mendanize AI's Tier 1 (public, ephemeral, embedded on content pages) hands off into Tier 2 (the Learner Account Area's `/account/ask`) when an anonymous visitor signs in to continue a conversation — never into the Admin Dashboard.
- All three surfaces share one design system (tokens, typography, color) but maintain distinct layout shells suited to their purpose. Per the Design Customization Principle, this shared design system is data-driven — every surface reads the same live settings store rather than holding its own fixed values.
- Content types (Articles, Learning Guides, AI Tools, Categories, Topics, Authors) are modules addressable from both the Teaching Frontend (public read) and the Admin Dashboard (authenticated management) — the Learner Account Area consumes the same content read-only, plus its own personalization layer (saved items, history, interests) that belongs to the `PublicUser`, not to the content models themselves.

This three-surface model does not replace the module list below — it defines _where_ each module is surfaced.

## DESIGN CUSTOMIZATION PRINCIPLE

Mendanize is a fully custom-built platform, not a template or theme. Because of this, nearly every visual aspect of the site can be exposed as an admin-configurable setting rather than a hardcoded value.

This applies across all three surfaces (Teaching Frontend, Learner Account Area, and Admin Dashboard, per Platform Architecture below):

- Brand assets (logo, favicon, colors, fonts)
- Theme presets (light/dark, palettes)
- Backgrounds (solid, gradient, pattern, image, video, animated)
- Typography (font selection, heading/body styles, sizes, spacing)
- Components (buttons, cards, forms, badges, modals — style, not behavior)
- Animation (hover effects, transitions, loading states)
- Navigation (header, footer, navbar, sidebar, menus)
- Homepage layout (section order, visibility)
- Blog/article appearance (layout, code block style, author cards, related content)
- Dashboard appearance (colors, widgets, analytics layout)
- SEO & social defaults (OG images, favicons, metadata)
- Media library (images, icons, video, illustrations)
- Design tokens (spacing, radius, shadows, breakpoints)

**What stays fixed, owned by developers, never exposed as a setting:**

- Underlying UI architecture and component logic
- Responsive behavior
- Accessibility behavior (semantic structure, keyboard nav, focus handling)
- Data models and business logic

The boundary is: _how something looks and whether it's visible_ is configurable; _how something behaves and is built_ is not. This mirrors how Notion, Shopify, and similar platforms balance flexibility with a consistent, polished product.

The full technical design for this system is split across two specs, not one: **MES-003** (Design System) defines the tokens and shared component library all three surfaces read from; **MES-020** (Platform Settings & Configuration) is the canonical owner of the settings store and admin UI that make those tokens runtime-editable. Every subsequent spec that touches visual design must state which of its decisions are fixed defaults (MES-003) vs. admin-configurable settings (MES-020).

## ENGINEERING PRINCIPLES

Every engineering decision should follow these principles:

- Build for long-term maintainability.
- Prefer reusable components.
- Avoid duplicated logic.
- Write readable code.
- Keep modules independent where possible.
- Favor composition over unnecessary complexity.
- Optimize performance by default.
- Follow consistent naming conventions.
- Design for future scalability.
- Prioritize developer experience.
