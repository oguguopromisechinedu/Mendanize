# Mendanize Engineering Specification (MES-030)
## Dual Authentication & Authorization Architecture

**Version:** 1.0
**Status:** Retrofit Specification — MES-001 through MES-028 are already implemented (per the MES-029 Production Readiness Report). This spec is not greenfield; it splits the existing single-domain auth system (built under MES-006) into two independent domains without breaking modules that already depend on it.
**Dependencies:** MES-006 (Authentication & User Management — being superseded by this spec's v2.0 update), MES-002 (Shared Services), MSEM Appendix A

Follows MSEM Appendix A — Security Baseline in full. No exceptions.

---

## OBJECTIVE

Split Mendanize's authentication into two completely independent systems:

1. **Public Authentication** — learners, readers, subscribers, customers, future premium members. `www.mendanize.com`.
2. **Admin Authentication** — internal staff only. `www.mendanize.com/dashboard`.

They share underlying infrastructure (Supabase Authentication, per MES-006) but must never share registration flows, UI, sessions, or user records.

---

## WHY THIS IS A RETROFIT, NOT NEW WORK

The following already exist and depend on the single-domain model MES-006 built:

- MES-019 (Ask Mendanize AI) — Tier 2 conversation history is scoped to "authenticated user."
- MES-021 (Billing) — `Subscription.userId` references the single user model.
- MES-022 (Personalization) — every saved-content/interest model references the single user model.
- MES-007 (Admin Dashboard) — currently gated by the same session/role check as public auth.

This spec must produce a migration plan for each of these, not just a description of the end state. Cursor should not delete and rebuild — it should introduce `PublicUser` and `Admin` as the split, migrate existing `User` records into the correct one based on their current role (Learner → PublicUser, everything else → Admin), and repoint the modules above at the correct new model.

---

## PUBLIC AUTHENTICATION (`www.mendanize.com`)

Create Account, Sign In, Forgot/Reset Password, Email Verification. Future: Social Login. Any valid email domain accepted.

Post-auth capabilities (unchanged from MES-006/MES-022): learning features, bookmarks, progress (future), purchases, profile management, newsletter, Ask Mendanize AI.

---

## ADMIN AUTHENTICATION (`www.mendanize.com/dashboard`)

Display **only**: Email, Password, Remember Me, Forgot Password.

**Must never display:** Create Account, Register, Sign Up, any social/OAuth login, Anonymous Login, Magic Link Login.

**Admin accounts cannot be self-created.** Every admin account is created by a Super Administrator from within the dashboard (Users & Roles, per MES-007's nav). Authorization is based on approved administrator records and assigned role/permissions — never an email-domain check alone.

---

## ROLE-BASED ACCESS CONTROL

Roles: Super Administrator, Administrator, Editor, Content Manager, Analytics Manager, Support Manager. Must be easily extendable — this is the RBAC layer MES-006/MES-007 already anticipated but didn't fully enforce; this spec is where enforcement actually lands.

Every request to `/dashboard/*` verifies: Authentication → Active Account → Assigned Role → Required Permission. No protected route trusts client-side role state.

---

## SESSION MANAGEMENT

Public and Admin sessions are **completely independent** — a public session must never grant dashboard access, and vice versa. This replaces MES-006's single session contract with two: `PublicSession` and `AdminSession`. Every module that previously referenced "the session" (Ask Mendanize AI, Personalization, Billing, Dashboard) must be updated to reference the correct one explicitly.

---

## DATABASE

New/updated models: `Admin, AdminRole, Permission, RolePermission, AdminSession, PublicUser, PublicSession, AuthorizationLog`.

**Migration required:** existing `User` records (from MES-006) split by role — Learner-role users become `PublicUser`, all other roles become `Admin`. Foreign keys in `Subscription` (MES-021), `SavedArticle`/`SavedGuide`/`SavedAITool`/`UserInterest`/`UserPreference` (MES-022), and `Conversation` (MES-019) are repointed to `PublicUser.id`.

---

## SECURITY

Permission validation, role validation, protected routes, session validation, audit logging (every admin action logged — this is new; MES-006 didn't require it), secure cookies, rate-limiting readiness, CSRF/XSS protection — per Appendix A, with audit logging as this spec's specific addition given elevated admin risk.

---

## WHAT NOT TO BUILD

Multi-factor authentication, SSO, enterprise identity providers, LDAP, OAuth administration — architecture-ready, not implemented.

---

## ACCEPTANCE CRITERIA

✓ Public and Admin authentication fully separated — no shared UI, registration, or sessions.
✓ Dashboard sign-in shows no registration/social/anonymous/magic-link options.
✓ Existing user data migrated without loss; Billing, Personalization, and Ask Mendanize AI continue functioning against the correct (`PublicUser`) model.
✓ RBAC enforced at the route and data layer, not just UI.
✓ Audit logging captures admin actions.
✓ Zero build/TypeScript/lint errors.

---

## STOP

1. Stop development.
2. Summarize the dual-auth architecture and confirm isolation between domains.
3. **Explicitly confirm the migration**: how existing users were split, and that Billing/Personalization/Ask Mendanize AI were repointed and tested against the new model.
4. Wait for approval before any further authentication enhancements.
