# Mendanize Engineering Specification (MES-021)
## Billing & Subscriptions

**Version:** 1.1 — corrected for the dual-authentication model (MES-006/MES-030). The original version routed billing through `/dashboard/*`, which is now Admin-only; subscriptions belong to `PublicUser`s and must live in the public account area instead.
**Status:** Feature Specification — closes a gap (premium subscriptions were a stated MES-001 business objective with no corresponding module)
**Dependencies:** MES-002 (Shared Services), MES-006/MES-030 (Dual Authentication), MES-020 (Platform Settings), MES-022 (User Learning & Personalization — shares the account area), MSEM Appendix A

---

## OBJECTIVE

Build subscription billing per MES-001's Business Objectives — premium subscriptions and sustainable revenue, without gating core educational content. Subscriptions belong to learners (`PublicUser`), not to `Admin` accounts — this module has no admin-facing billing surface beyond read-only reporting (see below).

---

## TIERS

Three-tier model — **Starter / Professional / Enterprise** — via Stripe. Exact per-tier feature gates are finalized once the feature modules they gate (AI usage limits, advanced analytics, etc.) actually exist; this spec builds the mechanism.

---

## PRINCIPLE

Per MES-001's Content Philosophy: monetization must never gate Articles or Learning Guides. Gating applies only to `PublicUser`-facing product features — Ask Mendanize AI usage volume, advanced SEO/analytics tooling (where applicable to learners), premium AI Tools directory features.

---

## BUILD

- Public `/pricing` page (read-only, no Stripe interaction, no auth required) presenting the three tiers.
- **`PublicUser` billing management** at `/account/billing` (part of the authenticated public account area alongside MES-022's My Learning Dashboard — explicitly *not* under `/dashboard/*`, which is Admin-only per MES-030) — subscription status, payment method, invoice history, plan change/cancellation.
- Stripe Checkout/Customer Portal integration for payment flows.
- Webhook handling to sync subscription status.
- **Admin-side, read-only:** a Subscriptions/Revenue report under the Admin Dashboard (`/dashboard/analytics` or a dedicated `/dashboard/billing-overview`, per MES-007's nav) — admins can view aggregate subscription/revenue data but never access or modify an individual `PublicUser`'s payment details directly; that stays inside the `PublicUser`'s own session per MES-030's isolation rule.

---

## DATA MODEL

`Subscription: id, publicUserId (references PublicUser.id, per MES-006/MES-030 — never a generic userId), tier, status (active/past_due/canceled), stripeCustomerId, stripeSubscriptionId, currentPeriodEnd`

---

## SCOPE OF THIS PHASE

Build: Stripe integration, data model (correctly keyed to `PublicUser`), public account billing UI, webhook sync, admin-side read-only reporting view.
Do NOT build yet: final per-tier feature gating logic (sequenced after the gated features themselves exist), enterprise custom contracts.
