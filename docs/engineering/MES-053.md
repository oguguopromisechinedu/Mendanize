---

## Objective

Extend MES-039’s Work Marketplace so a completed project is not a dead end. Clients can keep working with the same developer — via follow-on contracts, task requests, and (phase B) monthly retainers — while Mendanize keeps earning commission on the full website lifecycle, not only the first delivery.

This turns Work Marketplace from a one-shot hiring rail into a **relationship + maintenance** surface.

---

## Product story (canonical)

1. Client posts a job → developer hired → site built → client accepts → `Contract` → `COMPLETED`.
2. From that completed contract, client chooses **Continue Working** / **Hire Again**.
3. Mendanize opens a **continuation contract** linked to the original (same client + worker, same optional website label) — not a reopen of the finished contract.
4. Inside **Maintenance & Support**, the client can: request features/bugs, start a monthly plan, message the developer, view invoices/history, cancel maintenance anytime.
5. Developer accepts tasks, ships work, gets paid (task escrow and/or retainer).
6. Platform takes commission on initial project, continuation tasks, and retainers.

## Corrections (read before building)

1. **Do not reopen a `COMPLETED` contract.** Completion stays immutable for escrow history, reviews, and disputes. Ongoing work is always a **new** contract (or retainer) with `parentContractId` pointing at the completed root (or prior continuation).
2. **Do not invent a second chat system.** Maintenance chat = existing MES-043 thread between client and worker (deep-link from the contract panel).
3. **Do not invent a second dispute system.** Task / retainer payment disputes reuse MES-048 against the continuation contract / milestone.
4. **Do not route retainer money through MES-021 Checkout.** Retainers are Stripe Connect + Billing ([Connect subscriptions](https://docs.stripe.com/connect/subscriptions)): destination charges to the worker’s connected account, platform fee via `application_fee_percent` resolved from `MarketplaceCommissionRule` (WORK), same fee hierarchy as MES-052.
5. **Numbering note:** an older enterprise paste once used “MES-053” for ISO/SOC2 theater; that was rightsized into MES-035. This slot is reclaimable for a real product need — same pattern as MES-040 reclaiming a dropped number.

## Phase A — data model

### Extend `Contract`

```text
Contract
  kind              ContractKind   @default(PROJECT)   // PROJECT | CONTINUATION
  parentContractId  String?
  websiteLabel      String?        // client-facing name, e.g. "Acme Store"
  // existing: jobId, applicationId, clientId, workerId, status, …

  parent   Contract?  @relation("ContractLineage", …)
  children Contract[] @relation("ContractLineage")
```

Rules:

- `kind = PROJECT` — current behavior (hire from job posting).
- `kind = CONTINUATION` — created only from Hire Again / Continue Working; **same** `clientId` + `workerId` as parent; parent must be `COMPLETED` (or an earlier `CONTINUATION` that is `COMPLETED`/`ACTIVE` — allow chaining from the latest eligible in the lineage).
- Exactly one **ACTIVE** continuation between a given client–worker–root lineage at a time (enforced in service layer).
- Root lineage id = walk `parentContractId` to the original `PROJECT` contract (cached optional later; compute in Phase A).

### Continuity job (reuse, don’t fork escrow)

Continuation still needs a `JobPosting` + `JobApplication` for the existing Contract FK shape:

1. Create a **private** `JobPosting` with `status` never publicly listed (reuse `FILLED` / closed semantics; add `source = CONTINUATION` flag or `jobType = "maintenance"` catalog value used only for continuity — pick one, document in code).
2. Auto-create / auto-accept a `JobApplication` for the **same** worker (no open applications, no marketplace listing).
3. Create `Contract` with `kind = CONTINUATION`, `parentContractId`, optional `websiteLabel` copied from parent or edited by client.

No public jobs feed appearance. Moderation can still see these rows (Admin Marketplace domain).

### `MaintenanceTask`

```text
MaintenanceTask
  id, contractId          // continuation contract (ACTIVE)
  createdById            // client
  assigneeId             // worker (denormalized = contract.workerId)
  title, description
  type                   // FEATURE | BUG | CONTENT | SEO | PERFORMANCE | OTHER
  status                 // REQUESTED | ACCEPTED | DECLINED | IN_PROGRESS | SUBMITTED | DONE | CANCELLED
  priority               // LOW | NORMAL | HIGH
  milestoneId?           // when paid outside retainer (Phase A: usually set)
  createdAt, updatedAt, completedAt?
```

Phase A payment path: accepting a paid task creates (or attaches) a `Milestone` on the continuation contract → existing fund/release Connect flow. Unpaid / courtesy tasks allowed only if both parties agree (status path without milestone); default UX prompts a milestone amount.

## Phase A — flows

### Continue Working / Hire Again

1. Client opens completed contract workspace → CTA **Continue Working**.
2. Optional: set/confirm `websiteLabel`, opening note.
3. Service creates private job + accepted application + `CONTINUATION` contract.
4. Redirect to `/account/work/contracts/[continuationId]` with Maintenance & Support panel expanded.
5. Notify worker (MES-024 / EMS template event).

Worker may also be invited via a secondary **Hire Again** from client’s hiring history (same service).

### Maintenance & Support panel (completed PROJECT + ACTIVE CONTINUATION)

One section on the contract workspace (MES-052 surface), visible when:

- viewing a `COMPLETED` PROJECT (CTAs to start/join continuation), or
- viewing an `ACTIVE` / `COMPLETED` CONTINUATION (full panel).

Panel sections (one job each — no dashboard clutter):

1. **Status** — plan none / continuation active; parties; website label.
2. **Tasks** — list + create request (client); accept / decline / mark progress (worker).
3. **Messages** — deep link to MES-043 thread.
4. **Payments** — milestones + `ContractPayment` history for this contract and, on the root PROJECT view, a rollup of lineage payments (read-only).
5. **End maintenance** — client (or mutual) cancels ACTIVE continuation → `CANCELLED` (open milestones must be released/refunded via existing Connect paths or blocked until cleared — service rule).

### Invoices & payment history

No parallel ledger. Render existing `ContractPayment` + milestone rows for the lineage. Phase B adds retainer invoice rows from Stripe webhook sync (store Stripe invoice ids on `MaintenanceSubscriptionPayment`).

## Phase B — retainers (after Phase A)

### Catalog

Platform-default plans (Admin-configurable later; seed in code/DB for MVP):

| Tier | Intent (copy, not SLA law) |
|------|----------------------------|
| Basic Maintenance | Monitoring, small fixes, dependency bumps |
| Standard Support | Basic + content updates, minor features |
| Premium Support | Standard + priority response, larger monthly scope |

Workers may propose a custom monthly amount within Admin max bounds (settings flag); tiers remain labels for UX.

### `MaintenanceSubscription`

```text
MaintenanceSubscription
  id
  rootContractId         // original PROJECT
  continuationContractId // ACTIVE continuation workspace
  clientId, workerId
  tier                   // BASIC | STANDARD | PREMIUM | CUSTOM
  amountCents, currency
  status                 // TRIALING | ACTIVE | PAST_DUE | CANCELLED | INCOMPLETE
  stripeSubscriptionId
  stripeCustomerId       // platform Customer (destination-charge model)
  applicationFeePercent  // snapshot of rule at subscribe time
  cancelAtPeriodEnd Boolean
  currentPeriodEnd?
  createdAt, updatedAt
```

Checkout / create subscription per [Stripe Connect subscriptions — destination charges](https://docs.stripe.com/connect/subscriptions): Price + Customer on **platform**; `transfer_data.destination` = worker connected account; `application_fee_percent` from MES-052 WORK rule (or snapshot).

Webhooks (Connect + Billing): `customer.subscription.*`, `invoice.paid`, `invoice.payment_failed` → update status; write `MaintenanceSubscriptionPayment`; notify parties; surface PAST_DUE in panel.

**Cancel anytime:** client sets `cancel_at_period_end` (default) or immediate cancel when no open paid tasks require hold — product default = end of period.

### Tasks under retainer

Tasks may flag `coveredByRetainer = true` (no milestone). Abuse / overage is **policy + human decline**, not a metering engine in this MES. Optional future MES for hour banking.

Paid extras still use milestones on the continuation contract.

## Acceptance criteria

**Phase A**

1. From a `COMPLETED` PROJECT, client can start exactly one ACTIVE continuation with the same worker.  
2. Continuation never appears as an open public job.  
3. Maintenance & Support panel lists tasks; paid tasks fund/release via existing milestones.  
4. Messages deep-link to MES-043; disputes reuse MES-048.  
5. Ending maintenance cancels the continuation without mutating the original PROJECT row.  
6. Dual-auth + Connect/MES-021 separation unchanged.

**Phase B**

7. Client can subscribe/cancel a monthly plan; funds route to worker via Connect destination subscription with platform fee.  
8. Failed payment → `PAST_DUE` + notification; history visible in panel.  
9. Finance overview includes retainer fee totals.

Zero build/TS/lint errors for the phase being shipped.
