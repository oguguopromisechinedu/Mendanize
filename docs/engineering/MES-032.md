# Mendanize Engineering Specification (MES-032)
## Observability & Logging

**Version:** 1.0 — rightsized from the pasted "Enterprise Logging, Monitoring & Observability Platform" (MES-037). Kept: structured logging, error tracking, basic health monitoring, admin-facing status visibility. Dropped: distributed tracing across "regions," incident postmortem workflow, SOC-style Operations Center, retention tiers up to 730 days — none of that matches a single-region Vercel/Supabase deployment.
**Dependencies:** MES-002 (Shared Services — Logging Service, Audit Service), MES-007 (Admin Dashboard — Status Bar), MES-028 (Production Readiness — this spec is what MES-028 audits against), MSEM Appendix A

Follows MSEM Appendix A. No exceptions.

---

## OBJECTIVE
Give the Logging Service and Audit Service (already named in MES-002) real substance: structured error/warning logs, basic request tracing, and admin-visible health status — enough to know something broke before a user reports it, without building enterprise-grade infrastructure monitoring.

---

## LOGGING
Structured logs (level, message, module, timestamp, optional stack trace) for: application errors, warnings, AI generation failures, background job failures. One log format platform-wide — no module writes its own ad hoc console output.

## REQUEST TRACING (lightweight)
Every API request gets a request ID (per MES-002's response contract) that appears in any error log tied to that request — enough to trace a single failure end to end, not a full distributed tracing system.

## HEALTH STATUS
Feeds MES-007's Status Bar and AI & API Status panel: database reachable, each AI provider's last-known status (already scoped in MES-002), background job queue depth.

## ERROR TRACKING
Errors are classified (module, severity, timestamp) and visible in a simple Admin Dashboard log view — filterable, not a full incident-management workflow.

## RETENTION
Application logs: 30 days. Audit logs (admin actions, per MES-030): 1 year. No tiered multi-year retention policy needed at this stage.

---

## WHAT NOT TO BUILD
Distributed tracing across services/regions, incident management workflow with postmortems, third-party APM integration (deferred per MES-028), predictive failure detection.

---

## ACCEPTANCE CRITERIA
✓ Structured logging in place platform-wide. ✓ Request IDs traceable through error logs. ✓ Admin-visible health status and error log view exist. ✓ Retention policy applied. Zero build/TS/lint errors.

---

## STOP
Summarize completion. Confirm this closes the gap MES-028 previously only described as "architecture preparation." Wait for next spec.
