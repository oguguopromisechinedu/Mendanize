# Mendanize Engineering Specification (MES-051)

## Email Management System (EMS)

**Version:** 1.0 — drafted at full dashboard scope by explicit request. This is the Admin-facing control plane for **all** outbound email. It **extends** MES-042 (Transactional Email Delivery / transport) and MES-024 (Notification preferences + in-app), and **absorbs** the existing Newsletter admin module into one Communication domain — it does not invent a second SMTP stack or a parallel notification bus.  
**Status:** Complete (MVP) — see [MES-051-COMPLETION.md](../MES-051-COMPLETION.md)  
**Dependencies:** MES-002 (Notification Service dispatch facade, Audit, Logging), MES-003 (brand tokens for email chrome), MES-006/MES-030 (RBAC — Super Administrator / Admin / Editor), MES-007 (Admin Dashboard domain registration), MES-014 (logo/assets), MES-020 (secrets / provider keys remain settings-backed), MES-021 (subscription audience filters), MES-024 (preference gates, unsubscribe), MES-035 (marketing consent), MES-036/039/045 (automation event sources), MES-042 (canonical transport adapter), MSEM Appendix A

Follows MSEM Appendix A. No exceptions.

---

## OBJECTIVE

Let Super Admins (and permissioned staff) create, edit, test, schedule, enable, disable, and assign any email using any **verified `@mendanize.com` sender** — entirely from the dashboard — so product modules never hardcode subjects, HTML, or from-addresses again.

**One-line product rule:** application code emits a **named email event** (or enqueues a campaign); EMS resolves template + sender + variables + consent, then MES-042 delivers.

---

## CORRECTIONS / CONSOLIDATIONS (read before building)

1. **MES-042 stays the transport.** EMS configures providers and senders in the UI; it does not bypass the Notification/Email dispatch path with ad hoc `nodemailer` calls in feature modules.  
2. **MES-024 stays the preference + in-app owner.** Marketing/newsletter sends must check MES-024 prefs + MES-035 consent. Transactional auth mail (verification, reset) may bypass marketing opt-out but still uses EMS templates.  
3. **Existing `/dashboard/newsletter` is folded into EMS** (Newsletter subsection) — do not leave two competing campaign UIs. Redirect or replace the old route.  
4. **"Course" → Learning Guide** (MES-010). Variables use `{{guide_name}}` (alias `{{course_name}}` allowed for compatibility).  
5. **Audience "by Role"** means `PublicUser` capability flags / plan — never Admin RBAC roles as marketing segments. Admin invite mail is a separate transactional category.  
6. **Analytics honesty:** open/click tracking requires pixel + link wrapping via the provider or first-party redirects. If the chosen provider does not return a metric, show `—` / “unavailable,” not fake zeros presented as truth.

## 1. EMAIL TEMPLATES

Super Admin / permitted Admin can:

- Create, Edit, Duplicate, Preview, Send Test, Enable/Disable, Delete  

Each template record:

| Field | Notes |
|-------|--------|
| Name | Internal label |
| Internal description | Staff-only |
| Subject line | Supports variables |
| Sender name | Display name |
| From email | FK → verified Sender |
| Reply-To | Optional override |
| Category | FK → Email Category |
| Body HTML | Rich text / HTML editor |
| Body text | Auto or manual plain-text |
| Variables used | Declared / detected |
| Status | `DRAFT` \| `PUBLISHED` |
| Enabled | Soft kill-switch without unpublishing |
| Version history | Immutable snapshots on publish/save |

**Send Test:** pick recipient email(s); render with sample/fixture variable map; go through the same queue as production (tagged `TEST`).

**Delete:** Super Administrator only (see Permissions). Soft-delete preferred if the template is referenced by automations.

---

## 2. EMAIL CATEGORIES

Unlimited categories. Seed (editable, not hardcoded forever):

Welcome Email, Newsletter, Product Updates, AI Tool Announcement, Course Enrollment → **Guide Enrollment**, Certificate Issued, Password Reset, Email Verification, Magic Login Link, Security Alert, Account Notification, Subscription Activated, Subscription Expiring, Payment Successful, Payment Failed, Marketplace Purchase, Marketplace Sale, Marketplace Approval, Marketplace Rejection, Community Update, Survey, Event Invitation, Promotional Campaign, Custom.

Categories group templates and drive default analytics filters. System-critical categories (Verification, Password Reset, Security Alert) cannot be deleted while referenced; they can be renamed cautiously.

---

## 3. SENDER MANAGEMENT

Register unlimited professional addresses under the verified sending domain (initially `@mendanize.com`), e.g.:

`hello@`, `support@`, `newsletter@`, `learn@`, `marketplace@`, `billing@`, `community@`, `security@`, `notifications@`, `admin@`

Per sender:

- Address, display name default, reply-to default  
- Verification status (`PENDING` \| `VERIFIED` \| `FAILED`) — must match provider domain/DNS reality  
- Enabled flag  

**Only Super Administrator** may add/remove senders or mark verified. Templates may only select **Verified + Enabled** senders. No sending from arbitrary external domains in v1.

---

## 4. EMAIL VARIABLES

Built-in (extendable):

`{{user_name}}`, `{{first_name}}`, `{{email}}`, `{{verification_link}}`, `{{reset_password_link}}`, `{{guide_name}}` / `{{course_name}}`, `{{certificate_name}}`, `{{subscription_plan}}`, `{{tool_name}}`, `{{marketplace_item}}`, `{{current_date}}`, `{{current_year}}`

Custom variables: Admin-defined keys + description + sample value for preview. Render engine must escape HTML in variable values unless explicitly marked safe (links generated server-side for verification/reset).

Missing required variables on send → fail the queue item with a clear error (do not send half-rendered mail).

---

## 5. NEWSLETTER / CAMPAIGNS

Absorbs prior Newsletter admin:

- Create / Draft / Schedule / Publish  
- Save Draft, Send Immediately  
- Audiences: Everyone (consenting), Selected users, Subscription plan (MES-021), PublicUser tags/flags, custom segment filters  

Campaign states: `DRAFT` \| `SCHEDULED` \| `QUEUED` \| `SENDING` \| `SENT` \| `CANCELLED`.

Every recipient row becomes an Email Queue item. Respect unsubscribe + marketing consent (MES-035). Transactional categories are not used for blast campaigns.

---

## 6. AUTOMATION

Map platform events → template + optional delay:

| Event (examples) | Typical template |
|------------------|------------------|
| User registers | Welcome |
| Email verified | Thank you |
| Subscribes (MES-021) | Subscription activated |
| Marketplace purchase (MES-039) | Purchase receipt |
| Listing approved/rejected | Approval / Rejection |
| Guide/certificate completed | Certificate issued |
| Event invitation (MES-045) | Event invitation |

Rules: enable/disable, template FK, sender override optional, condition JSON (light). **No visual Zapier builder in v1** — table of rules is enough.

Modules fire `email.emit(eventKey, payload)` (or Notification Service equivalent); they never embed HTML.

---

## 7. EMAIL ANALYTICS

Dashboard metrics (provider-backed where available):

Total Sent, Delivered, Opened, Clicked, Bounced, Failed, Unsubscribed, Spam Complaints, Open Rate, Click Rate, Delivery Rate.

Filter by date, category, template, campaign, sender. Store aggregates + optional per-message events. Do not rebuild MES-023; email metrics live in EMS and may emit summary `AnalyticsEvent`s if useful.

---

## 8. EMAIL QUEUE

Operational list:

Statuses: `PENDING` \| `SENDING` \| `COMPLETED` \| `FAILED`  

Actions: Retry, Cancel (if not completed). Show template, recipient, provider message id, error, attempts, timestamps. Workers use MES-042 transport with bounded retries (MES-032 logging).

---

## 9. EMAIL SETTINGS

Super Administrator configuration:

- SMTP and/or API provider credentials (stored via MES-020 secrets pattern — never in git)  
- Default sender, default reply-to  
- Brand logo, footer HTML, company address, social links  
- Unsubscribe footer (required on marketing)  
- Tracking: open pixel / click wrapping on|off  

Changing provider must not require app code deploys — config only.

## WHAT NOT TO BUILD

- A second Notification Service or bypass of MES-042  
- Full ESP clone (A/B testing suites, heatmaps, deliverability war rooms) in v1  
- Sending as non-`@mendanize.com` (or unverified) domains  
- SMS/push as part of EMS (stay MES-024)  
- Learner-facing “email builder”  
- Multi-tenant white-label ESP for Organizations (MES-040/047 out of scope here)

---

## ACCEPTANCE CRITERIA

1. Super Admin can manage templates, senders, categories, variables, newsletter, automations, queue, analytics, and settings from **Communication → Email Management**.  
2. Any published+enabled template can be assigned to an automation or campaign **without code changes**.  
3. From-address is always a verified EMS sender.  
4. Auth verification/reset use EMS templates + MES-042 transport.  
5. Marketing sends honor unsubscribe/consent.  
6. Permission matrix enforced; Editors cannot publish or configure SMTP.  
7. Old newsletter UI is merged or redirected.  
8. Zero build/TS/lint errors.

## RELATIONSHIP TO MES-042

| MES-042 | MES-051 |
|---------|---------|
| Transport adapter, prod fail-loud, auth wiring | Dashboard EMS, templates, senders, campaigns, automations, analytics, queue, settings |

Implement **MES-042 first** (or in the same effort as EMS settings + minimum verification/reset templates). EMS without transport is UI-only; transport without EMS keeps hard-coded templates — both incomplete alone.
