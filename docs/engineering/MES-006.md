# Mendanize Engineering Specification (MES-006)
## Authentication & Authorization Foundation

**Version:** 2.0 — supersedes the original MES-006 (v1.0, single-domain). This version establishes the foundation with the dual-domain split in mind from the start; MES-030 is where the split is actually retrofitted into the already-built platform.
**Dependencies:** MES-002 (Shared Services), MES-003 (Design System), MSEM Appendix A

Follows MSEM Appendix A — Security Baseline in full. No exceptions.

---

## NOTE ON SEQUENCING

If you are reading this after MES-001–029 are already built (per the MES-029 Production Readiness Report), do not re-implement this spec from scratch — it describes the target foundation. **MES-030 is the actual retrofit spec**; apply that one against the live codebase. This document exists so the foundation spec and the built system agree on what "done" looks like, and so any future rebuild starts from the dual-domain model directly instead of single-domain first.

---

## OBJECTIVE

Build a secure authentication foundation supporting two completely independent systems from the outset:

1. **Public User Authentication** — learners, readers, subscribers, customers.
2. **Internal Administration Authentication** — Mendanize staff only.

Shared underlying infrastructure (Supabase Authentication), separate user experiences, authorization policies, and access controls.

---

## DOMAIN 1 — PUBLIC (`www.mendanize.com`)

Create Account, Sign In, Forgot/Reset Password, Email Verification. Future: Social Authentication.

---

## DOMAIN 2 — ADMINISTRATION (`www.mendanize.com/dashboard`)

Sign In, Forgot Password, Remember Me — **only**. Never: Create Account, Register, Sign Up, any social login, Anonymous Login, Magic Link Login.

**Admin accounts cannot be self-created** — only an authorized Super Administrator creates new admin accounts, from within the dashboard.

---

## AUTHORIZATION (RBAC)

Roles: Super Administrator, Administrator, Editor, Content Manager, Analytics Manager, Support Manager — extendable.

---

## SESSION MANAGEMENT

Independent sessions per domain — `PublicSession` and `AdminSession` — never shared, never cross-granting access.

---

## DATABASE

Models: `PublicUser, Admin, Role, Permission, RolePermission, PublicSession, AdminSession, PasswordReset, EmailVerification, AuditLog`.

---

## SECURITY REQUIREMENTS

Secure password hashing, secure cookies, CSRF/XSS protection, input validation, rate limiting, audit logging, session validation, route protection — per Appendix A. Never trust client-side authorization.

---

## ROUTE PROTECTION

Public routes stay public. Protected public routes require an authenticated `PublicUser`. Dashboard routes require an authenticated `Admin` with the correct permission. Unauthorized access redirects to the correct domain's login — never the other one's.

---

## INTEGRATION

Every module built after this spec (Ask Mendanize AI, Billing, Personalization, Analytics, Notifications, Settings) references `PublicUser` for learner-facing data and `Admin` for dashboard-facing data — never a generic shared `User`.

---

## ACCEPTANCE CRITERIA

✓ Public and Admin authentication architectures both exist and are fully isolated.
✓ Dashboard has no registration path.
✓ RBAC prepared.
✓ Protected routes implemented for both domains.
✓ Zero build/TypeScript/lint errors.

---

## STOP

Verify security, authorization, protected routes, and session isolation. Summarize. Wait for approval.
