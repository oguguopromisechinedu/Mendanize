# Mendanize Engineering Specification (MES-034)
## Backup & Recovery

**Version:** 1.0 — rightsized from the pasted "Enterprise Backup, Disaster Recovery & Business Continuity Platform" (MES-038). Kept: automated database/media backup, restore capability, basic verification. Dropped: named RTO/RPO enterprise targets, multi-region/geo-redundancy, immutable storage, scheduled recovery-testing program, "Recovery Center" dashboard with checksum validation UI — none of this matches a single Supabase Postgres instance.
**Dependencies:** MES-002 (Shared Services), MES-014 (Media Library), MSEM Appendix A

Follows MSEM Appendix A. No exceptions.

---

## OBJECTIVE
Make sure Mendanize's data — content, media, settings, user accounts — can actually be restored after accidental deletion or a bad migration. This is table stakes for any production app, not an enterprise differentiator.

---

## DATABASE BACKUP
Rely on Supabase's built-in automated daily backups (point-in-time recovery, per Supabase's own plan tier) rather than building a custom backup service — this is the pragmatic choice for the current stack. Confirm the plan tier includes the retention window needed (check Supabase's current offering) and document the restore procedure.

## MEDIA BACKUP
Media Library assets (MES-014) are already stored in Supabase Storage, which has its own redundancy — no separate backup pipeline needed at this stage. Document the restore path if a bucket is misconfigured.

## CONFIGURATION BACKUP
Platform Settings (MES-020) and Design Customization values are database-backed, so they're covered by the database backup above — no separate mechanism needed.

## MANUAL SAFETY NET
Before any risky migration (schema change, bulk data operation — including MES-030's user-record migration), take a manual snapshot and document the rollback steps. This is a process requirement for the team, not a feature to build.

## RECOVERY DOCUMENTATION
A short, real runbook: how to restore from a Supabase backup, how to verify data integrity after restore, who has the authority to trigger a restore (an `Admin` action, logged per MES-030's audit requirement).

---

## WHAT NOT TO BUILD
A custom backup service, multi-region replication, a "Recovery Center" dashboard, scheduled recovery-testing automation, enterprise RTO/RPO commitments — all disproportionate to a single-database, single-region app at this stage. Revisit if/when Mendanize has enterprise customers with contractual DR requirements.

---

## ACCEPTANCE CRITERIA
✓ Confirmed Supabase backup coverage matches the current plan tier. ✓ Restore runbook documented. ✓ Manual pre-migration snapshot process is the team's standard practice. Zero build/TS/lint errors (this spec is mostly process/documentation, not new code).

---

## STOP
Summarize completion. Confirm the restore runbook exists and has been reviewed. Wait for next spec.
