# Mendanize Engineering Specification (MES-002)
## Shared Services & API Architecture

**Version:** 1.0
**Status:** Foundation Specification — NEW, inserted to close a structural gap
**Dependencies:** MES-001 (Vision), MSEM Appendix A (Engineering Standards)

---

## WHY THIS SPEC EXISTS

Without a shared services contract defined early, every later module (Articles, AI Tools, Search, Analytics) ends up inventing its own data-fetching patterns, its own notion of "related content," and its own AI configuration. That already happened once — the previous sequence built four separate recommendation implementations and two conflicting AI settings screens before anyone noticed. This spec exists so that doesn't happen again.

Every module spec from this point forward builds against these services rather than each rolling its own.

---

## SHARED SERVICES

Each is a single, canonical implementation — other modules call it, none re-implement it.

### Content Service
Owns fetching and querying Articles, Learning Guides, AI Tools, Categories, Topics, Authors — one query layer regardless of which surface (public or dashboard) is asking, respecting the public/authenticated read boundary already established.

### Recommendations Service
Owns "related content" and "recommended for you" logic platform-wide. Every module that needs related/recommended content (Search, Personalization, Analytics, public Article/Guide/Tool pages) calls this one service. See the dedicated Recommendations Engine spec later in this sequence for its internal design — this entry just establishes that it is the *only* place that logic lives.

### AI Service
Owns the interface to AI providers — **multi-provider from the start** (Claude/Anthropic, OpenAI, Gemini, Grok, DALL-E), one client per provider behind a single internal interface, with a per-provider connection status surfaced in the dashboard (AI & API Status panel). Every AI-assisted feature calls through this service rather than holding its own provider integration — this includes both Ask Mendanize AI (learner-facing, per MES-018) and the Admin AI Studio (content-generation — article writing, image generation via DALL-E, video generation — a distinct admin-facing capability, not to be confused with Ask Mendanize AI).

### Search Service
Owns query execution across the Content Service's indexed data.

### Notification Service
Owns all in-app and email notification dispatch, referenced by Auth, Content workflows (publish notifications), and Billing (payment notifications).

### SEO Service
Owns metadata resolution (title/description/OG/structured data) for any content type, using the Metadata Template system.

### Media Service
Owns asset storage, retrieval, and the reusable Media Picker component's data layer.

### Settings Service
Owns platform configuration reads — including the Design Customization settings store and platform-wide settings (Platform Settings module, AI configuration, etc.). This is the **single canonical owner of AI configuration** — no other module (including Ask Mendanize AI's own dashboard) redefines AI settings; it reads from and links to this service's settings screens.

## API ARCHITECTURE

- One consistent response shape across all internal API routes: `{ data, error, meta }`.
- Authentication/authorization checked at the service layer, not duplicated per-route.
- Route organization mirrors the surface split: `/api/public/*` (read-only, no auth) and `/api/dashboard/*` (authenticated).
- Versioning is not implemented yet, but routes are namespaced (`/api/v1/*`) so it can be introduced later without a breaking restructure.
- Every route validates input against a schema before touching a service — no service trusts its caller.

---

## HOW LATER MODULES USE THIS

Every module spec from here on states, where relevant: "Uses the Content Service for X, the Recommendations Service for related content, calls the AI Service for Y" — instead of defining its own data access or duplicating logic. If a module spec doesn't explicitly say it's building new shared logic, assume it should be calling one of the services above.

---

## SCOPE OF THIS PHASE

Build: the service layer interfaces (even as thin wrappers initially — real implementations grow as each module lands), the API route structure and response contract, the validation pattern.
Do NOT build yet: the actual Recommendations logic (its own future spec), the actual AI provider wiring (its own future spec) — this phase defines the *seams*, not every implementation.
