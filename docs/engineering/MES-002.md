# Mendanize Engineering Specification (MES-002)
## Shared Services & API Architecture

**Version:** 2.0 — reorganized and updated to fold in MES-031's AI Knowledge Generation Pipeline concepts (AI Gateway, Dashboard AI Orchestrator) into the AI Service, and to cleanly group all thirteen shared services in one place (v1.0/v1.1 added six services after the API Architecture section rather than alongside the rest — fixed here).
**Status:** Foundation Specification
**Dependencies:** MES-001 (Vision), MSEM Appendix A (Engineering Standards)

---

## WHY THIS SPEC EXISTS

Without a shared services contract defined early, every later module (Articles, AI Tools, Search, Analytics) ends up inventing its own data-fetching patterns, its own notion of "related content," and its own AI configuration. That already happened once — the original ChatGPT-drafted sequence built four separate recommendation implementations and two conflicting AI settings screens before anyone noticed. This spec exists so that doesn't happen again.

Every module spec from this point forward builds against these services rather than each rolling its own.

---

## SHARED SERVICES (all thirteen, canonical)

Each is a single implementation — other modules call it, none re-implement it.

### Content Service
Owns fetching and querying Articles, Learning Guides, AI Tools, Categories, Topics, Authors — one query layer regardless of which surface (public or dashboard) is asking, respecting the public/`PublicUser`/`Admin` read boundary established in MES-006/MES-030.

### Recommendations Service
Owns "related content" and "recommended for you" logic platform-wide. Every module that needs related/recommended content (Search, Personalization, Analytics, public Article/Guide/Tool pages) calls this one service — see MES-018 for its internal design.

### AI Service
Owns the interface to AI providers — **multi-provider from the start** (Claude/Anthropic, OpenAI, Gemini, Grok, DALL-E), one client per provider behind a single internal interface, with per-provider connection status surfaced in the dashboard (AI & API Status panel, MES-007). Every AI-assisted feature calls through this service:

- **Ask Mendanize AI** (learner-facing conversational answers, MES-019)
- **Admin AI Studio** (admin-triggered content generation — article writing, image generation via DALL-E, video generation, MES-011)
- **AI Gateway** — the knowledge-first search step of MES-031's pipeline: before any generation happens, this checks existing published content via the Content Service. This is a mode of the AI Service, not a separate service.
- **Dashboard AI Orchestrator** — the automated-generation step of MES-031's pipeline, triggered when the AI Gateway finds a genuine knowledge gap. It calls the same generation capability as the Admin AI Studio (MES-011) — it does not duplicate that logic, it invokes it asynchronously and routes the result into the `AI Draft` queue instead of directly to an admin's manual session.

No feature holds its own provider integration outside this service.

### Search Service
Owns query execution across the Content Service's indexed data (MES-017).

### Notification Service
Owns all in-app and email notification dispatch — referenced by Auth (MES-006/MES-030), Content workflows (publish notifications), Billing (payment notifications, MES-021), and MES-031's admin-review alerts.

### SEO Service
Owns metadata resolution (title/description/OG/structured data) for any content type, using the Metadata Template system (MES-015).

### Media Service
Owns asset storage, retrieval, and the reusable Media Picker component's data layer (MES-014) — including AI-generated images from MES-011 and MES-031.

### Settings Service
Owns platform configuration reads — the Design Customization settings store and platform-wide settings (MES-020), including AI configuration. This is the **single canonical owner of AI configuration** — no other module (Admin AI Studio, Ask Mendanize AI, or the AI Knowledge Pipeline) redefines AI settings; all three read from and link to this service's settings screens.

### Learning Service
Owns Guide/Lesson progress state, difficulty/duration metadata queries, and structure (sections/lessons) reads — used by the Admin Dashboard's Learning domain (MES-007) and the public Guide experience (MES-026).

### Analytics Service
Owns writing to and reading from the `AnalyticsEvent` stream (MES-023) — every module that needs to record or query an event uses this, not its own tracking logic.

### Homepage Service
Owns reading/writing Homepage section configuration (MES-013) — the Homepage Builder (MES-007's dashboard domain) and the public Homepage (MES-005) both read through this.

### Navigation Service
Owns menu structure and Menu Location resolution (MES-016) — used by both the Public Layout header/footer (MES-004) and the Admin Dashboard's own navigation (MES-007).

### Logging Service
Owns structured application logging (errors, warnings, performance traces) — feeds the Admin Dashboard's System Status/Status Bar (MES-007) and the Production Readiness observability prep (MES-028).

### Audit Service
Owns the `AuditLog` — every `Admin` action (per MES-030's audit logging requirement) is recorded through this service, not logged ad hoc per module. Also logs every MES-031 AI Draft generation and review action, since those are Admin-side events even when triggered by a public question.

## API ARCHITECTURE

- One consistent response shape across all internal API routes: `{ data, error, meta }`.
- Authentication/authorization checked at the service layer, not duplicated per-route.
- Route organization mirrors the surface split: `/api/public/*` (read-only, no auth, or authenticated as `PublicUser` where relevant) and `/api/dashboard/*` (authenticated as `Admin` only). Per MES-006/MES-030, these are two independent auth domains — no route or service checks a generic "authenticated user"; every check is explicitly against `PublicUser` or `Admin`.
- **The one exception is MES-031's pipeline trigger**: a `PublicUser`-originated request (a chat question) can enqueue a job that the AI Service/Orchestrator processes and writes to `Admin`-owned tables. This is a backend service call, never a direct write from the public request — the `PublicUser` session never touches `/api/dashboard/*` to do this.
- Versioning is not implemented yet, but routes are namespaced (`/api/v1/*`) so it can be introduced later without a breaking restructure.
- Every route validates input against a schema before touching a service — no service trusts its caller.

## HOW LATER MODULES USE THIS

Every module spec states, where relevant: "Uses the Content Service for X, the Recommendations Service for related content, calls the AI Service for Y" — instead of defining its own data access or duplicating logic. If a module spec doesn't explicitly say it's building new shared logic, assume it should be calling one of the thirteen services above.

**Launch-tier additions (MES-032–035) build on these services rather than adding new ones:** MES-032 (Observability) gives the Logging Service and Audit Service real substance. MES-033 (Caching) is a cross-cutting layer over the Content/AI Services, not a fourteenth named service. MES-034 (Backup) relies on Supabase's own infrastructure rather than a custom service here. MES-035 (Privacy & Compliance) uses the Audit Service for its export/deletion trail. None of them expand this thirteen-service list — that's deliberate.

## SCOPE OF THIS PHASE

Build: all thirteen service layer interfaces (thin wrappers initially — real implementations grow as each module lands), the API route structure and response contract, the validation pattern, the `PublicUser`→`Admin` one-way trigger pattern used by MES-031.
Do NOT build yet: the actual Recommendations logic (MES-018), the actual AI provider wiring (MES-011/MES-019), the actual knowledge-gap detection logic (MES-031) — this phase defines the *seams*, not every implementation.
