# Mendanize Engineering Specification (MES-042)

## Transactional Email Delivery

**Version:** 1.0 — rightsized from the long-standing Gap C2 (auth verification/reset and MES-024 notifications depend on real SMTP, not `CommunicationLog status:"queued"` forever).  
**Status:** Complete (MVP) — see [MES-042-COMPLETION.md](../MES-042-COMPLETION.md)  
**Dependencies:** MES-002 (Notification Service owns dispatch), MES-006/MES-030 (verification + password reset), MES-020 (Platform Settings — provider keys), MES-024 (templates + preference gates), MSEM Appendix A
Follows MSEM Appendix A. No exceptions.

---

## OBJECTIVE

Wire a real transactional email transport so verification, password reset, and notification emails actually leave the platform in production — without building a marketing ESP or a second notification system.

---

## TRANSPORT

- One provider adapter behind the existing Notification Service (e.g. Resend, Postmark, or SMTP).  
- Configured via Platform Settings / env (MES-020) — never hardcoded.  
- Failures logged via Logging Service (MES-032); retries are bounded, not infinite.  
- Dev/test may still log-only when no provider is configured; production must refuse silent success if email is required for the action.

---

## TEMPLATES

Reuse MES-024's template model. Minimum live templates:

1. Email verification  
2. Password reset  
3. Generic notification (in-app counterpart already exists)  

HTML + plain-text. Brand tokens from MES-003 where practical. No per-module ad hoc HTML email builders.

---

## AUTH INTEGRATION (MES-006)

`/api/auth/register` and the server-action register path must both send the same verification email. Password reset must send a real message with a single-use token. Dual-auth: public templates for `PublicUser`; admin invite/reset templates for `Admin` (MES-030) — never mix session types.

---

## WHAT NOT TO BUILD

Multi-ESP failover orchestration. In-app chat or push as a substitute for email delivery. A full Email Management dashboard (templates CMS, sender registry, newsletter studio, automation builder, analytics UI) — that is **MES-051**. This spec only guarantees transport + the minimum auth templates until EMS lands; once MES-051 is implemented, those templates become EMS seed data and MES-042 stays the send adapter only.

---

## ACCEPTANCE CRITERIA

✓ Production verification and reset emails deliver end-to-end. ✓ Notification email path uses the same transport. ✓ Missing provider fails loudly in prod for auth-critical flows. ✓ Preference unsubscribe / marketing consent (MES-035) respected. Zero build/TS/lint errors.

---

## STOP

Confirm auth + notification emails share one transport. Proceed to **MES-051** for the full Email Management System dashboard when ready.
