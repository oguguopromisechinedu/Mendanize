# Mendanize Engineering Specification (MES-028)

## Performance, Security & Production Readiness

**Version:** 1.1 — expanded to cover MES-031–035, which didn't exist when this spec was first written and were previously missing from its scope entirely. **Dependencies:** All prior specs (MES-001–027), MES-030 (Dual Authentication & Authorization Architecture), MES-031 (AI Knowledge Generation Pipeline), MES-032 (Observability & Logging), MES-033 (Caching & Performance), MES-034 (Backup & Recovery), MES-035 (Privacy & Compliance Basics), MSEM Appendix A

---

## OBJECTIVE

Audit every module against the standards defined in MSEM Appendix A — Accessibility, Responsive, Performance, SEO, Code Quality, Security Baseline, Testing Baseline — and close any gaps. This is an audit against a standard every module was already built against, not the first time these concepts are introduced (that was the core weakness of the original sequence, fixed by extracting Appendix A at MES-002).

---

## SCOPE

Every module: Public Website, Auth (dual-domain, MES-006/MES-030), Admin Dashboard, Articles, Categories/Topics, Guides, AI Tools, AI Studio, AI Knowledge Generation Pipeline (MES-031), Homepage CMS, Media Library, SEO Center, Navigation, Search, Recommendations, Ask Mendanize AI, Platform Settings, Billing, Personalization, Analytics, Notifications, Observability (MES-032), Caching (MES-033), Backup (MES-034), Privacy & Compliance (MES-035), and all three public content experiences.

---

## PERFORMANCE AUDIT

Verify Server Component boundaries, bundle size, image/font loading, code splitting, Core Web Vitals on every public page (per Appendix A) — not just the homepage.

## SECURITY AUDIT

Verify the Security Baseline was actually followed per-module, not just present in the appendix: input validation, output sanitization, authorization at the data layer, session handling via MES-006/MES-030's two independent contracts (`PublicSession` and `AdminSession` — confirm no module still references a single generic session), no exposed secrets, rate-limit-ready design on search/AI/forms, RBAC actually enforced (not just prepared) on every `/dashboard/*` route per MES-030.

## SHARED SERVICES AUDIT

Confirm no module duplicated logic that belongs in a Shared Service (MES-002) — specifically check that Recommendations (MES-018) has exactly one implementation, AI configuration (MES-020) has exactly one screen, and no module reinvented session handling. **Verify MES-031's one-way boundary crossing specifically**: confirm no code path lets a `PublicUser` session read, list, or otherwise access the AI Draft queue or AI Knowledge Center — this is the one place in the platform where a public action creates admin-side data, and it's the one most worth a deliberate check rather than assuming the spec's intent was followed.

## ERROR HANDLING

Consistent Error Pages, Empty States, Retry Components, Fallback UI across every module — reusable, not per-module reinvention.

## OBSERVABILITY

Architecture prepared for structured logging, error reporting, performance monitoring, audit logging, health checks — placeholder integrations, real wiring is post-launch infrastructure work.

## DATABASE & API REVIEW

Relationship integrity, naming consistency, timestamp consistency, indexing preparation across every model introduced since MES-006. API response shape consistency per MES-002's contract.

## CODE QUALITY

Folder structure, naming conventions, dead code removal, duplicate code reduction — platform-wide sweep.

## TESTING

Expand the testing scaffolding that started in MES-002 (Appendix A Testing Baseline) into real coverage: unit tests for shared components, integration tests for each module's core flows, accessibility tests, initial performance regression tests. Full E2E suite is MES-029's responsibility to verify, not build fresh here.

---

## WHAT NOT TO BUILD

Third-party monitoring integration, real rate limiting, real CDN/infrastructure provisioning, external DevOps pipelines — architecture and interfaces only.

---

## ACCEPTANCE CRITERIA

✓ Every module passes the Appendix A audit. ✓ No duplicated shared-service logic remains. ✓ Error handling and testing scaffolding are consistent platform-wide. ✓ Zero build/TS/lint errors anywhere in the codebase.

---

## STOP

Produce a Production Readiness Report: what was found, what was fixed, what remains for external infrastructure. Wait for MES-029.
